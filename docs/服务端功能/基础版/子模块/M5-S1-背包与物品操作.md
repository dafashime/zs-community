# M5-S1 背包与物品操作

> 所属主模块:[M5-物品与装备](../主模块/M5-物品与装备.md)

## 功能概述

覆盖玩家背包(`g_data.bag`,上限 48 格)的全部服务端交互:进图全量拉取、增量增删改、地面物品感知、拾取、丢弃(含金币)、使用物品(CM_EAT 及其特殊 stdMode 分支)、堆叠叠放(CM_PILEUPITEM 特殊编码)、拆分(CM_SPLITITEM)、背包耐久变化。
英雄侧镜像消息(CM_HERO_* / SM_HERO_*)归 [M9](../主模块/M9-英雄系统.md),本文只标注差异点。

## 详细报文说明

### 1. SM_BAGITEMS(201)——背包全量

- 时机:客户端进图收到 SM_LOGON 后主动发 `CM_QUERYBAGITEMS`(81)(`mir2.scenes.main.ground.lua :: processMsg` SM_LOGON 分支);或玩家点整理按钮(节流 1s,`mir2.scenes.main.panel.bag.lua :: ctor` 整理按钮回调)。服务端也可在任意时刻用它做权威全量同步。
- TDefaultMessage:**四标头全部无意义**,客户端不读(msg 只剩 ident 生效)。
- body:`TClientItem` 连续数组。解析循环 `while bufLen > 0 do … net.record(item, buf, bufLen)`(`mir2.data.bag.lua :: set`)——**没有数量前缀,param/recog/tag/series 都不是数量**,条数只由字节数决定。单条尺寸 = 16 + 4×KeyValueSize(见主模块 §2.2),服务端必须保证 body 长度恰为 Σ单条尺寸,否则解析错位污染后续所有消息。
- 客户端行为:清空重建 `items` 列表;处于 fusion/strengthen 面板中的 makeIndex 被跳过(不进背包列表但仍在 wire 数据里);快捷栏按名字重新绑定。
- 错误分支:无应答码;若服务端漏发,背包为空且后续增量会错乱(不阻塞消息队列,无 setWaitMsg)。

### 2. CM_QUERYBAGITEMS(81)

- 时机:见上。
- 字段:四标头全空,body 空(net.send({CM_QUERYBAGITEMS}) → dataLen=0)。
- 应答:SM_BAGITEMS(201)。整理语义即"以服务器顺序重排背包",客户端 reload 按 1..48 线性摆放。

### 3. SM_ADDITEM(200)

- 时机:拾取成功(见 §8)、购买到货(M6)、任务/NPC 发放、叠加产物等一切"新实例入包"。
- 字段:四标头不读。
- body:TClientItem 数组(`mir2.data.bag.lua :: add` 循环解析,通常 1 条)。每条触发 tip "「名称」被发现",并回调 helper.runner.onNewItem 与 draw.ufact.UseItem(自动拾取/穿戴辅助逻辑)。
- 收尾:处理完调用 `PileUpItem()`(ui.lua 内嵌函数,230-247 行):若存在可合并的两堆且不在拆分流程中,自动补发一条 CM_PILEUPITEM(见 §9)。
- 错误分支:无显式失败;**背包满**时服务端不应下发本消息(旧协议有 SM_GETSTORAGEITEM_FULLBAG 等专用码,背包本身无 FULL 回执——未核实旧服务端是否用文本 SM_SYSMESSAGE 提示)。

### 4. SM_DELITEM(202)

- 字段:`recog = MakeIndex`;`param` 双分支(`mir2.scenes.main.ui.lua` 490-508 行):
  - **param=0**:从 `g_data.bag`、`g_data.equip`(已穿装备!)、strengthen 面板三处同时尝试删除。即服务端删除已装备物品也用本消息(param=0)。
  - **param=1**:仅删仓库面板条目(delItem + delItemData)——仓库侧删除专用(见 S3)。
- body:无。
- 注意 tag/series 不读。

### 5. SM_UPDATEITEM(203)

- 时机:耐久外的属性变化(绑定态 normalStateSet、升级标记、扩展键变化、改名等);也用于叠加后的源堆数量刷新(未核实旧服务端习惯,推断:叠加结果通常以"目标堆 UPDATEITEM + 源 DELITEM"表达)。
- body:**单条 TClientItem**(16+4n)。客户端先在 `g_data.bag` 匹配(makeIndex 且 name 相同才替换,`mir2.data.bag.lua :: upt`),再原样 buf 又喂给 `g_data.equip:upt`——同一条消息既可更新背包也可更新已穿装备,匹配不上则静默丢弃。strengthen 面板若持有该物品也会同步。
- 服务端注意:makeIndex 必须保持不变;name 变化会导致匹配失败(客户端故意要求 name 一致防止串位)。

### 6. SM_DELITEMS(709)

- body:N × uint32 MakeIndex,`count = floor(bufLen/4)`(ui.lua 537-557 行)。
- 对每个 id:从 bag、equip 两处删除并解绑快捷栏。**param/recog/tag/series 不读**。
- 适用:系统批量回收(如活动清场);普通单件删除仍建议 SM_DELITEM(202)。

### 7. SM_ITEMSHOW(610)/ SM_ITEMHIDE(611)——地面物品

- SM_ITEMSHOW 字段(`mir2.scenes.main.ground.lua :: processMsg` 243-250 行):
  - `recog` = 物品实例 id(地面唯一标识,拾取/隐藏都靠它)
  - `param` = 地图 x;`tag` = 地图 y
  - `series` = looks(物品外观贴图号,直接用于 dnitems 资源渲染)
  - body = `TFloorItem`(非 packed,总 24 字节):

    | 偏移 | 类型 | 字段 | 说明 |
    |---|---|---|---|
    | 0 | char*[15] | name | 定长 16 字节 GBK 区(0x00 补齐),**无长度前缀**(readChars 语义) |
    | 16 | int | owner | 归属者 id(0=无主;客户端不深究具体值) |
    | 20 | byte | state | 状态标记;客户端仅判断 >0 → 名字染紫(好货/归属提示,map.map.lua::showItem 827-844 行) |
    | 21 | — | 填充 | fillCheck(4) 补齐 3 字节 0x00,**必须发送**,否则消费偏移错位 |

    (state 具体位含义未核实;owner 的判定逻辑如"归属保护期内他人不可拾"由服务端自行执行——客户端不做本地拦截。)
- SM_ITEMHIDE:`recog`=id,`param`=x,`tag`=y(body 无)。客户端按 id 移除。
- 补充:SM_DISAPPEAR 分支在此构建只剩 print 调试(ground.lua 257 行),对象消失统一走 SM_ITEMHIDE。

### 8. CM_PICKUP(1001)——拾取

- 时机:玩家点击/自动拾取判定通过后(`controller.pickupTest`,1049-1057 行)。
- 节流:`lastPickupTime`,`socket.gettime()` 差 ≤0.3s 直接不发。
- 字段:`param = player.x`,`tag = player.y`;**recog/series 不填**(不带目标物品 id!服务端按坐标+距离自行决定拾起哪个物品)。
- body:无。
- 应答:
  - 成功:无 PICKUP 专用回执。物品经 **SM_ITEMHIDE(对周围广播)+ SM_ADDITEM(对拾取者)** 表达。客户端没有处理任何名为 SM_PICKUPGOODS/CM_PICKUPFAIL 的消息(grep 全树无引用)。
  - 失败:同样无专用码;可用 SM_SYSMESSAGE 文本提示(归 M4-S4),客户端不会因此回滚任何状态(因为请求前并未预扣物品)。
- 服务端要点:校验距离(客户端允许站在相邻格发起,是否放宽由服务端定)、归属保护(state>0 的私有时限)、背包容量与负重。

### 9. CM_PILEUPITEM(1115)——叠放(特殊编码详解)

- 时机一(手动):背包内把可堆叠物 A 拖到 B 上(`panel.bag.lua :: putItem`,247-254 行);仓库面板同样支持(S3,series 恒 0)。
- 时机二(自动):SM_ADDITEM/SM_ITEM_PILEUP_RESULT 结束后 `PileUpItem()` 扫描全包找可合并对(`bag:PileUpNext/AutoItemAdd`,isCanPileUp 全条件判定)逐次发送。
- 字段(**目标/源编码极易搞反,务必按下表**):

  | 标头 | 值 | 含义 |
  |---|---|---|
  | recog | 目标堆 makeIndex(uint32 直存 int32) | 合并被并入的那一堆 |
  | param | Loword(源 makeIndex) | 源(被合并方)低 16 位 |
  | tag | Hiword(源 makeIndex) | 源高 16 位 |
  | series | isHero:0=主角色,1=英雄 | 英雄包叠放置 1(ui.lua PileUpItem(isHero)) |

  即服务端还原源 MakeIndex = `MakeLong(param, tag)` = param | tag<<16。
- body:无。
- 流控:客户端发出后置 `g_data.player.IsinPileUping=true`,在收到 **SM_ITEM_PILEUP_RESULT(3322)** 前不再发下一条(手动路径亦如此)。服务端必须对每次 CM_PILEUPITEM 回一条 3322,否则自动叠放链卡死(不再有后续叠加,但不阻塞其他消息)。
- SM_ITEM_PILEUP_RESULT(3322):`series`=0 主角色 /1 英雄(客户端据此选择 g_data.bag / g_data.heroBag 继续 PileUpItem);recog/param/tag 不读。body 无。
- 结果数据流:合并成功后服务端应随后下发"目标堆 SM_UPDATEITEM + 源 SM_DELITEM"(此组合为推断——客户端对叠加结果本身不做本地推演,一切以这两条增量为准;未核实旧服务端确切顺序)。

### 10. CM_SPLITITEM(1116)——拆分

- 时机:可堆叠物品(dura>1)提示框点"拆分"输入数量(`itemInfo.lua :: splitItem`,639-685 行)。入口含背包/英雄背包/**仓库**三种 from。
- 字段:

  | 标头 | 值 |
  |---|---|
  | recog | 源堆 MakeIndex |
  | param | 拆出数量(整数,客户端校验 0<count≤dura) |
  | tag | 恒 0 |
  | series | isHero:params.from=="heroBag" 时 1,否则(背包/仓库)0 |

- body:无。
- 应答(组合推断,客户端按通用增量消费):
  - 背包拆分:源堆 SM_UPDATEITEM(数量减少)+ 新堆 SM_ADDITEM;
  - 仓库拆分:新堆经 **SM_STORAGE_ADDITEM(717)** 下发(body=TClientItem,`panel.storage.lua :: splitNemItem` 加入仓库),源堆走 SM_UPDATEITEM 或 SM_STORAGEITEMDURACHG(未核实旧服务端选择)。
  - 失败:无专用回执;客户端 `IsSplliteItem` 标志会在下一次 SM_ITEM_PILEUP_RESULT 处理链中复位(ui.lua 231/246 行),不会永久卡死。

### 11. CM_DROPITEM(1000)/ CM_DROPGOLD(1016)/ 应答

- CM_DROPITEM:拖出背包松手触发(`item.lua :: throw`)。贵重物(def.items.filt[名].isGood)先弹确认框。字段:`recog`=MakeIndex,strs={物品名}(GBK,net.send 组装);param/tag/series 空;body 仅 strs 编码(名称 + 0x00 分隔占位)。
  - 客户端立即把物品移入 `bag.throwing` 暂存区并从 UI 移除(乐观回滚模型)。
  - **SM_DROPITEM_FAIL(601)**:`recog`=MakeIndex → `throwEnd(false)` 把物品放回背包并刷新面板(ui.lua 560-565 行)。
  - 成功路径:客户端引用了常量 `SM_DROPITEM_SUCCESS`,但 globa1 从未定义(nil 死分支,ui.lua 558 行)→ 成功时**没有也不需要**专用回执;服务端只需广播 SM_ITEMSHOW 给周围、并对丢弃者后续的背包状态保持一致(暂存区残留是客户端已知瑕疵,不影响协议)。SM_DROPITEM_OK(600) 同样无处理分支,发了也无害但无意义。(未核实旧服务端实际发送哪一种)
- CM_DROPGOLD:`recog`=金币数量(input 数字),其余空。应答走 SM_GOLDCHANGED(653,recog=新余额,归 M8-S4)+ 周围玩家看到地面金堆的 SM_ITEMSHOW(looks 为金币贴图,由服务端定)。

### 12. CM_EAT(1006)/ SM_EATITEM_OK(635)/ SM_EATITEM_FAIL(636)——使用物品

- 时机:双击背包物品且 `getTakeOnPosition(stdMode)` 返回 nil(非穿戴类)时(`item.lua :: use` else 分支)。stdMode=4(技能书)先弹确认框再发。
- 字段:`recog`=MakeIndex;**param/tag/series/body 全空、无 strs**——服务端只能凭 makeIndex 找到物品并按其 stdMode/shape 决定效果。
- 客户端乐观扣减:发前把物品从 items 移入 `bag.eat` 暂存;节流:同类操作 5 秒内不重复(`bag:use` limit=5;force 参数时 0.2s,快速连用按钮走 force=false 默认值——itemInfo release() 的连续使用是 0.5s 间隔循环至多 6 次,受同一 5s 闸门限制,第二次会被吞,属客户端既有行为)。
- 应答:
  - **SM_EATITEM_OK(635)**:四标头不读。物品真正消失;若为传送石类还触发 autoRat 停止(checkUsedItemforStopAutoRat)。
  - **SM_EATITEM_FAIL(636)**:四标头不读(recog **不是**错误码表——客户端未解析任何错误编号,文案需另发 SM_SYSMESSAGE)。物品放回背包。
- 特殊 stdMode 分支(均在 item.lua :: use / itemInfo.show):
  - stdMode=47 名"传情烟花":改发 **CM_YANHUA_TEXT(1290)**,recog=MakeIndex,strs={玩家输入文字};不直接 EAT。
  - stdMode=47 名"金条":确认框后照常 CM_EAT(服务端兑现 998000 金币,经 SM_GOLDCHANGED)。
  - stdMode=159(活力水晶):先发 **CM_V_POWERSTONE(4644)** recog=MakeIndex → **SM_V_POWERSTONE(4644)** 弹确认框:param=0 可用(tag=今日还可个数,series=1 表示领取后需客户端自删图标)/1 活力上限/2 今日次数上限;玩家确认后客户端才发 **CM_EAT**(recog=同 makeIndex)。同号双向,服务端注意 ident 相同方向区分。
  - stdMode=46(天赐宝箱/钥匙):转入宝箱流程,详见 [M5-S4](M5-S4-强化合成与宝箱.md)。
  - 装备栏符咒位(U_BUJUK)上的祝福罐/泉水罐/魔令包"收集"按钮:**CM_DBLCLICKUSEITEM(1017)**,recog=罐子 MakeIndex,param=U_BUJUK(9)(itemInfo.lua 619-630 行)。应答未接专用分支(推断走通用 SM_UPDATEITEM/SM_ADDITEM 表达产出,未核实)。

### 13. 耐久变化(SM_BAGITEMDURACHG 641)

- 时机:背包内物品持久/数量被服务端改动(消耗品计数、武器磨损入包时等)。
- 字段(`ui.lua` 525-534 行):`recog`=MakeIndex,`param`=新 dura,`tag`=新 duraMax,`series`=价格(客户端签名带 price 但仅透传,显示不用——未核实用途,建议填 0)。
- body:无。作用域:bag + strengthen 面板;已穿装备走 SM_DURACHANGE(见 S2)。

### 14. SM_WEIGHTCHANGED(622)

- `g_data.player:weightChanged(msg.recog, msg.param, msg.tag)`——三个标头分别作为 (weight/maxWeight/wearWeight?) 传入(data.player 实现,具体槽位映射见 M4-S1 引用;本模块只记录:三值均来自标头,body 无)。

## 服务端实现要点

1. **TClientItem 是唯一物品载体**:保证 KeyValueSize 与实际键值数一致;packed 无填充;name 经 Index 由客户端本地表解析,线上 TClientItem **不含名字**,服务端不必(也无法)传名字——地面物品名字走 TFloorItem。
2. **数量语义**:堆叠物 dura=剩余个数;满堆 dura==duraMax 不可作叠放目标也不能作源(isCanPileUp 拒绝),发放整组时直接给 dura=duraMax 的单条即可。
3. **删除必带正确 param**:背包装备 0、仓库 1;批量用 709。
4. **CM_PICKUP 无目标 id**:按 x/y(可容差)自选物品;归属保护完全由服务端裁决。
5. **叠放握手**:每条 CM_PILEUPITEM 必须回 SM_ITEM_PILEUP_RESULT(series 正确),否则客户端自动叠放链停摆。
6. **丢弃失败必须显式回执** SM_DROPITEM_FAIL,否则客户端物品停留在 throwing 暂存区(UI 已不可见)。
7. CM_EAT 类"使用"一律无参数,效果完全服务端裁决;失败记得回 SM_EATITEM_FAIL 让客户端回滚物品。
