# M8-S4 货币与充值

> 所属主模块:[M8-经济交易系统](../主模块/M8-经济交易系统.md)

## 功能概述

两条主线:

1. **货币余额同步**:金币(SM_GOLDCHANGED)与"元宝/钻石/礼券/银两"五件套(SM_GETDIAMNUM_EXT,body=TMessageCapitalInfo)全部为**服务端主动推送**——本构建客户端不存在任何"请求刷新货币"的 CM 报文(已全树核实,见下)。交易/摆摊/寄售造成的余额变化都依赖这两条推送落地。
2. **充值(iOS IAP)**:客户端向游戏 TCP 服务器申请订单号(CM_GHOME_PAY_READY),调起苹果支付;**收据验证走 HTTP 登录中心 `/paycb`**,验证通过后客户端轮询游戏服务器发货结果(CM_QUERY_GHOME_ORDER → SM_SEND_GHOME_ORDER_RESULT);余额最终由 SM_GETDIAMNUM_EXT 同步。`gplus.lua`(Android 渠道)为空壳,无任何网络行为。

## 详细报文说明

### 货币五件套:SM_GETDIAMNUM_EXT(1202)

- 触发时机:**纯服务端推送**。已核实客户端全树没有任何发送侧调用(grep `GETDIAMNUM` 仅命中常量定义与本处理分支),即**不存在"何时主动请求刷新货币、CM_=多少"的答案——没有这个 CM**。典型推送点由服务端自定:充值到账、摆摊/寄售扣款、消费等。
- body 校验:`bufLen == getRecordSize("TMessageCapitalInfo")`(=24)才解析,**长度不符静默丢弃**(`mir2.scenes.main.ui.lua` 行 274~282)。

body = TMessageCapitalInfo(6×int32 小端,无填充):

| 偏移 | 类型 | 字段 | goldNum 映射(mir2.data.player.lua :: setCapitalInfo) | 含义 |
|---|---|---|---|---|
| 0 | int | linfu | gird | 礼券 |
| 4 | int | yuanbao | gold(**注意:字段名叫 gold,存的是元宝**) | 元宝 |
| 8 | int | diamon | diamond | 钻石 |
| 12 | int | limitLf | limtGird | 礼券上限 |
| 16 | int | silver | silver | 银两/金币类二级货币((未核实)具体展示位) |
| 20 | int | silverExp | silverExp | 银两经验/利息((未核实)) |

布局详情与属性页展示另见 [M4-S1 玩家属性与能力](../子模块/M4-S1-玩家属性与能力.md)(TMessageCapitalInfo 的权威描述归该文档,本文只记触发时机与映射)。收到后除更新数据外,还会刷新 equip 面板 attributes 页(若开着)并调 `infoBar:uptYb`(本构建为空实现)。

### 金币:SM_GOLDCHANGED(653)

- recog = int32 **变动后的金币总量**(不是差量)。`common.goldChanged`:新值大于旧值时提示"+N 金币增加.",更新 g_data.player.gold、刷背包金币、播钱音效,再调 `infoBar:uptGold`(空实现)。
- 买卖、交易交割、摆摊费用等都以此同步;客户端不回包。

### 实名认证:SM_PLAYER_AUTHEN(4636)

- `g_data.credit:setAuthen(msg)`:`isAuthen = (msg.recog == 0)`。
- 该标志唯一用途:`panel/common/item.lua`(行 635、650)丢弃物品时附加文案"未验证角色丢弃物品后其他玩家无法拾取"。属于信用/实名体系的最小残留实现。
- 客户端无请求报文(CM_REFRESH_CREDIT(1059) 定义未用),推送时机由服务端定(登录后/认证状态变化,(未核实))。

### 充值订单流(GHOME,游戏 TCP + HTTP 混合)

商品目录为客户端本地硬编码的 iOS 产品 id:`com.umir2.no1.YB6/18/28/68/100/198/328/498/648`(对应 6~648 元档,"N元宝",`mir2.single.iap.lua :: productsInfo`)。非 iOS 平台充值页显示"当前仅支持通过iOS客户端进行充值"。

**前置**:进图流程中服务端发 `SM_LOGON_64ID(4651)`,body 为 64 位角色 id 的原始 8 字节,客户端**不解码**直接存为 `IAP.roleIdentify` 并初始化 IAP(`mir2.scenes.main.ground.lua` 行 70~73)。所有订单归属判断都基于它。

完整时序(文字步骤):

1. 玩家在商城面板充值页点购买并确认 → `shop:addPayOrder(identifier)`:若已有进行中订单则拒绝("当前正在处理其他订单");否则记 payOrder 并发 **CM_GHOME_PAY_READY(4482)**(无参无 body)。
   - 变体:客户端启动/界面恢复时 `shop:checkUnfinishOrder()` 若发现没有待验证收据却存在脏状态,也会发一条**不带 recog 的 CM_GHOME_PAY_FAILED(4483)** 清理。
2. 服务端创建订单,回 **SM_GHOME_PAY_READY(4482)**:
   - `recog` = int32 订单号;
   - `buf` = extend 字符串(服务端生成的透传凭据,客户端原样存入 payOrder.extend);
   - 客户端 `onPayReady`:recog<0 且无未完成收据 → 视为下单被拒,自动重走步骤 1;recog≥0 → 组装订单数据 `{o=订单号, e=extend, id=roleIdentify, name=角色名}`,经 XXTEA(key=`ec_umir2_payment`)+hex 编码后传给 iOS 原生 IAP 发起支付(`iap.paymentWithProduct`)。
3. 支付结束,原生回调 `onPaymentEvent`:
   - PURCHAED → `iap.onPurchaed`:订单归属不是当前角色 → 提示并缓存;否则查本地已验证缓存,已验证直接跳步骤 5,未验证进入步骤 4。
   - FAILED → 发 **CM_GHOME_PAY_FAILED(4483)**(recog=订单号)通知服务端作废,清本地订单。
4. 收据验证(HTTP,**不是游戏 TCP**):`game.loginer:verifyReceipt` 向登录中心发 **`POST http://<logincenter>/paycb`**,表单字段:

| 字段 | 含义 |
|---|---|
| productid | 苹果产品 id(com.umir2.no1.YBxx) |
| gameorderid | 游戏订单号(字符串化 recog) |
| iosreceipt | 苹果收据(receipt) |
| extend | 步骤 2 下发的 extend 透传串 |
| tid | 苹果 transaction_id |

   响应 JSON `{code, des, ...}`:`code==-112`(或 `res.status==0`)视为验证成功;其他 code → onVerifyFailed 终止。HTTP 层自带 3 次指数退避重试(loginer.send_)。
5. 验证成功 → `shop:onPurchaed`:立即发 **CM_QUERY_GHOME_ORDER(4484)**(recog=订单号),并用定时器**每 12 秒重发一次**直到拿到结果——服务端必须能幂等处理重复查询。
6. 服务端发货完成回 **SM_SEND_GHOME_ORDER_RESULT(4484)**:
   - `recog` = 结果码。命中错误码表(-98 系统忙、-7~-14 登录中心转发错误段)时**客户端保持轮询**(onPayResult 直接 return,定时器继续);
   - 其他值 → 订单终结:清定时器与 payOrder,通知 UI(onPayResult)。
   - 元宝到账本身经 **SM_GETDIAMNUM_EXT(1202)** 推送体现。
7. `SM_GHOME_UNFINISH_ORDER(4485)`:客户端分支为空注释,无任何逻辑(保留兼容即可)。

### gplus.lua 结论(Android 渠道)

`mir2.single.gplus.lua` 全部函数(`init/login/logout/getTicket/pay/extendFunction/call`)都是**空函数体**,仅保留 `appid="791000255"` 与监听器注册骨架。**没有任何网络调用、没有 CM 报文**——本构建的 Android 充值链路不存在。服务端无需为其实现任何协议。(如实结论,任务清单第 4 点的核查结果:iap/gplus 中真正与游戏服务器交互的只有上文 GHOME 三条 CM;iap 本身也不直连游戏服验证收据。)

### credit.lua 是什么(任务清单第 5 点)

不是礼券也不是积分,而是**实名/信用认证标志**:仅一个布尔 `isAuthen`,唯一数据源是服务端推送 SM_PLAYER_AUTHEN(4636)(recog==0 即已认证),唯一消费点是丢物提示文案(见上)。相关报文仅此一条;CM_REFRESH_CREDIT(1059) 在本构建无发送点。

## 附注:panel.top.lua 不是货币栏(任务边界澄清)

`mir2.scenes.main.panel.top.lua` 经核实为**排行榜面板**(个人榜/英雄榜/声望榜,页签 mafa/mars/fasheng/respect/heroall 等),与顶部货币显示无关:

- 请求:`CM_QUEST_ORDER(1060)`,`recog`=页码(0 起,-1 查自己,-2 无榜返回),`param`=榜类型(0~3 个人、4~7 英雄、8 出师),节流 top/4 秒(`top :: query`);
- 应答:**`SM_ORDER_LIST(1108)`**(`ui.lua` 行 1211 → `panel.top:processUpt(msg.param, msg, buf, bufLen)`):`recog`=当前页(-2 未上榜/-1 无数据),`param`=榜类型回显,`tag`=sortType(客户端仅 ==2 时按心法条目渲染),`series`=总页数;body 按 param 分支解析定长条目数组:0~3 单人榜 → `TXinfaNormalOrderItem{string charName[15]; int value; int xinfaLv}`(24B),4~7 英雄榜 → `THeroOrderItem{string masterName[15]; string heroName[14]; short level}`(34B)/`TXFHeroOrderItem`(40B,心法榜),8 出师榜 → 同单人榜条目;`page==-2` 时弹"你的英雄没有上榜/你没有上榜"提示,-1 或空 body 直接忽略。

该功能不属于经济交易模块,详细展开归排行榜所属文档(不在 M8 系列内)。真正的"货币栏"刷新路径只有上文两条推送(SM_GOLDCHANGED/SM_GETDIAMNUM_EXT)+空实现的 infoBar:uptGold/uptYb。

## 服务端实现要点(依客户端行为推断)

1. **货币必须服务端推**:客户端没有任何余额请求手段,漏推一条 SM_GETDIAMNUM_EXT 就会一直显示旧值直到下次推送。所有扣加元宝/钻石/礼券/银两的操作(商店、摆摊元宝单、寄售、充值)完成后都要补推。
2. **SM_GETDIAMNUM_EXT 长度敏感**:客户端按 `bufLen==getRecordSize` 精确匹配,多发/少发字节等于没发。
3. **SM_GOLDCHANGED 语义是总量**:recog 必须给扣/加之后的绝对值;客户端靠前后差值播报。
4. **订单号 int32**:SM_GHOME_PAY_READY.recog 与 CM_QUERY_GHOME_ORDER.recog 都是 int32;extend 透传串建议限长(客户端无校验,过长会撑大后续 XXTEA 数据)。
5. **轮询幂等**:CM_QUERY_GHOME_ORDER 每 12s 一发,处理必须幂等;"仍在处理"用错误码段(-7~-14/-98)应答让客户端继续等,最终态用其他码。
6. **paycb 与游戏服解耦**:收据验证在登录中心(HTTP),发货指令在游戏服(TCP);两者需要共享订单表。验证成功但玩家不在线时,应支持离线入账+上线后 SM_GETDIAMNUM_EXT 补发。
7. **跨角色订单**:IAP 收据可能属于其他角色的 roleIdentify(客户端会拒绝并提示"请前往处理"),服务端/paycb 应按 extend/id 入账到正确角色而非当前连接角色。
