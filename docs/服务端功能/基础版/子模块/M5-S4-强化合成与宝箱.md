# M5-S4 强化合成与宝箱

> 所属主模块:[M5-物品与装备](../主模块/M5-物品与装备.md)

## 功能概述

三组"材料 → 产出"玩法:
1. **首饰合成**(panel.fusion):5 件同名首饰 + 1 件助熔剂,消耗元宝合成更高阶首饰;含查询(可合成目标/价格)与提交两步。
2. **衣服强化**(panel.strengthen):赤月首饰×3 + 金刚石×888 强化雷霆/烈焰/光芒系衣服(CM_UPDATE_CLOTHES)。
3. **天赐宝箱 Box2**(panel.treasureBox):stdMode=46 宝箱 + 对应钥匙道具开启、转动、领奖。

另列已定义但本客户端**未接入**的升级/合成消息族,供服务端规避。
`mir2.helperScript.mod.equip.lua`(82KB)经全文件 grep **不含任何 net.send / CM_ / SM_ 引用**,是纯本地换装辅助逻辑(一键穿装等只操作本地数据并复用 item:use 的常规 CM_TAKEONITEM 单件发送),不存在批量组合 CM 报文——见文末专节。

## 详细报文说明

### 1. CM_STRENGTHEN_EQUIP_QUEST(4465)/ SM_STRENGTHEN_EQUIP_QUEST(4465)——合成查询

- 时机:向格子 1 放入第一件首饰时自动发送(`fusion:addItem`,379-383 行)。同号双向。
- CM 字段:`recog`=该首饰 MakeIndex;param/tag/series/body 空。
- SM 应答(`fusion:addItems`,697-753 行):
  - **成功(param==1)**:

    | 标头 | 含义 |
    |---|---|
    | recog | level(熔锭等级,0..4 → 决定助熔剂 looks=level+5579 与替换品文案"祖玛/赤月/雷霆/强雷/战神") |
    | tag | price(缺一件材料的元宝单价,客户端按 count*price 显示) |
    | series | 目标物品个数 N |

    body:N 个 **short**(小端 int16)为目标物品种类 Index 列表——注意此处不走 record 系统,而是 `ycByteStream:readShort((i-1)*2)` 手工读取(fusion.lua 702-708 行),即 N×2 字节紧凑排列,无填充。Index 是 wupin.txt 行号,客户端据此显示目标外观与属性 tips。多目标表示随机取一。
  - **失败(param≠1)**:错误码表:

    | param | 文案 |
    |---|---|
    | 0 | 包裹中没有这件物品 |
    | 2 | 此物品不可升级 |
    | 3 | 目前还不能合成这个等级的装备 |

    客户端把全部已放材料退回背包(itemsBack2bag)。body 无。
- 服务端要点:QUEST 应答决定整个面板的定价与助熔剂校验口径(level);若玩家放入的首饰等级与服务端记录不一致,后续正式提交会以服务端为准回错误码。

### 2. CM_STRENGTHEN_EQUIP(4466)/ SM_STRENGTHEN_EQUIP(4466)——提交合成

- 时机:点"开始合成"并确认弹窗(`fusion.lua` ctor 内确认按钮,136-162 行)。
- CM 字段:**recog/param/tag/series 全部不填**(net.send({CM_STRENGTHEN_EQUIP}, nil, data))。
- body:`{"int", makeIndex}` 数组(net.send data 数组逐项 writeInt,小端 int32 紧凑):格子 1..6 中实际放置的物品 MakeIndex 依序排列(最多 6 个:5 首饰 + 1 助熔剂;用元宝补材料时对应项缺失)。**无数量前缀**,条数 = bodyLen/4,服务端按此解析。
- SM 应答(`fusion:fusionEquip`,755-778 行):
  - `param=1`:成功——播放特效、清空面板(g_data.bag.fusion 重置)。产物由服务端以通用增量下发(SM_ADDITEM 新首饰;材料消失可用 SM_DELITEMS(709) 批量或逐条 SM_DELITEM;元宝扣减走 M8-S4 资金消息)。此增量组合为推断(客户端不做本地推演)。
  - `param≠1` 错误码:

    | param | 文案 |
    |---|---|
    | 3 | 参与合成的装备数量不正确 |
    | 4 | 装备不能合成 |
    | 5 | 元宝数量不足 |
    | 6 | 目前不能合成该等级物品 |
    | 7 | 放入的催化剂不正确 |
    | 8 | 不可合成绑定装备 |
    | 9 | 放入装备必须相同 |
    | 10 | 包裹中没有这个物品 |
    | 11 | 正在处理元宝交易,请耐心等待 |

    (0/1/2 无映射。)失败时材料保留在面板,玩家可取回或再试。
- 流控:拖入材料有 2s 节流(checkLastTime("fusion",2)),提交本身无节流,服务端自行限频。

### 3. CM_UPDATE_CLOTHES(4637)/ SM_UPDATE_CLOTHES(4637)——衣服强化

- 时机:strengthen 面板(与 fusion 共用素材 UI)确认弹窗(strengthen.lua 137-161 行)。要求:格 1-3 = 赤月级首饰(圣战/法神/天尊 × 戒指/项链/手镯)、格 4 = 金刚石且 dura≥888、格 5 = 雷霆战甲/烈焰魔衣/光芒道袍之一。
- CM 字段:`recog`=格 5 衣服的 MakeIndex;其余标头空。
- body:`{"int", makeIndex}` ×4(格 1..4 的 MakeIndex,小端 int32 紧凑,16 字节定长)。
- SM 应答(ui.lua 1760-1769 行):
  - `recog=0`:成功,播放特效。产物/材料变化同样走通用增量(推断)。
  - `recog≠0`:`strengthen:showError` 错误码表:

    | recog | 文案 |
    |---|---|
    | -1 | 未在背包中找到这件装备 |
    | -2 | 放入的衣服不符合要求 |
    | -3 | 这件装备已经升级了三次,不能再升级了 |
    | -4 | 未提供足够的赤月装备 |
    | -5 | 提交的金刚石不足 |
    | -6 | 很遗憾升级失败 |

    注意 -6 是"业务失败"(消耗是否扣除由服务端策略决定,客户端不区分)。

### 4. 天赐宝箱(Box2)

#### 4.1 开箱:CM_BOX2_TRYOPEN(1085)

- 时机:双击背包中 stdMode=46 物品(`item:use` → `useTreasureBox`,item.lua 321-397 行)。客户端用硬编码名单配对:
  - 箱名:紫铜/白银/赤金/神秘/新年/节日/春节/火龙/王者/玛法 + "天赐"
  - 钥匙名:同前缀 + "钥匙"
  在全背包搜索配对物的 MakeIndex;两者齐备才发送(任一缺失静默返回)。
- 字段:

  | 标头 | 值 |
  |---|---|
  | recog | **箱子** MakeIndex |
  | param | Loword(**钥匙** MakeIndex) |
  | tag | Hiword(钥匙 MakeIndex) |
  | flag | 代码里写了 flag=0,但 net.send 不消费该键——线上无此字段 |

- body:无。
- **SM_BOX2_TRYOPEN(961)**(ui.lua 2577-2582 行):
  - `recog=0`:成功。`param`=boxType(0/1 用 prguse3 动画档位,≥2 用 prguse2);body = TBox2PrizeItem 数组直到耗尽(panel.treasureBox :: ctor 87-92 行 while 循环)。TBox2PrizeItem(非 packed,**24 字节/条**):

    | 偏移 | 类型 | 字段 | 说明 |
    |---|---|---|---|
    | 0 | string[15] | name | 首字节长度 L + L 字节 GBK,字段占 16B |
    | 16 | int | looks | 奖品外观 |
    | 20 | int | amount | 数量(客户端未消费数值,仅展示外观) |
    | — | 填充 | | fillCheck(4):21→24,补 3 字节 |

    前 12 格为转盘展示(其中第 9 格为中心大奖位,9..12 为累计领取区)。
  - `recog≠0`:body=错误文案(net.str 直接 tip),不开面板。
- 开箱成功后钥匙/箱子的扣减时序由服务端定(推断:首次 ROTATE 时扣一把钥匙;未核实)。

#### 4.2 转动:CM_BOX2_ROTATE(1086)/ SM_BOX2_ROTATE(962)

- CM:第一次(openTimes==0)**不带任何标头**;之后每次把当前背包中钥匙的 MakeIndex 编进 param/tag(Loword/Hiword)(treasureBox.lua 43-79 行)。无 body。
- SM:`recog=0` 成功,`param`=最终停格索引(onRotate 动画终点);`recog≠0` 时 body=错误文案 tip。
- 客户端每次转动 openTimes+1;服务端应校验钥匙库存并控制单箱最大次数(客户端在 openTimes>3 后领奖即关箱,见下)。

#### 4.3 领奖:CM_BOX2_GETPRIZE(1087)/ SM_BOX2_GETPRIZE(963)/ 关闭 CM_BOX2_CLOSE(1088)

- GETPRIZE:双击中心大奖格触发(双击间隔判定 0.6s,treasureBox.lua 203-231 行);**无标头无 body**。
- SM_GETPRIZE:`recog=0` 成功,`param` 透传给 onGetPrize(param>0 且 openTimes≤3 时展示下一档奖励动画;openTimes>3 或 ==0 则客户端自动发 CM_BOX2_CLOSE 并关面板);`recog≠0` body=错误文案。
- CLOSE:关面板时发送;客户端对 CLOSE **没有任何应答分支**(服务端可静默处理,用于结算未领取奖励——语义未核实)。
- 奖品入包:走通用 SM_ADDITEM(推断;BOX2 族自身不带物品数据)。

### 6. helperScript.mod.equip.lua 专项核查(任务点名项)

- 文件约 84KB,为本地"换装方案/一键穿装"辅助脚本。
- grep 结果:`net.send`、`CM_`、`SM_`、甚至 `send`/`msg` 关键字**零命中**。
- 结论:它不产生任何额外网络报文;一键穿装的每件装备仍走 `common.item :: use()` 的标准单件 CM_TAKEONITEM(1003) 序列(受 bag:use 5s 同类防抖影响,实际表现为逐件排队穿戴)。服务端无需为其实现批量协议。(该文件属 rebuilt-src 基础版树;若未来引入白猪 mod 树的批量换装,需另行分析。)

## 服务端实现要点

1. **两个 4465/4466 与 4637 都是同号双向**;方向只能靠帧内 ident 无法区分 C/S——网关层按流向即可,服务端解析无歧义。
2. CM_STRENGTHEN_EQUIP / CM_UPDATE_CLOTHES 的 body 是**裸 int32 数组**(无 record 包装、无数量头),长度即条数;与其他域的 Loword/Hiword 编址不同,这里 makeIndex 直传 int。
3. QUEST 应答中的目标 Index 列表是 short 紧凑数组(手工 readShort),不是 record;多目标=随机池,单目标也建议给 1 条保持一致。
4. 宝箱链路(TRYOPEN→ROTATE×N→GETPRIZE→CLOSE)是无状态的多次往返,每次 ROTATE 都要重新验证钥匙;失败统一用 `recog≠0 + GBK 文案 body` 表达,客户端直接 tip。
5. 所有"成功"都只回结果码,产物一律走 S1 的通用增量(SM_ADDITEM/SM_DELITEM(S));不要发明新的产物承载字段。
6. 绑定规则:isBinded(normalStateSet bit1)的装备禁止合成(错误码 8),服务端需在提交时复查扩展键值而非信任客户端。
