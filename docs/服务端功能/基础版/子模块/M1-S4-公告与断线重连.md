# M1-S4 公告与断线重连

> 所属主模块:[M1-登录与接入](../主模块/M1-登录与接入.md)

## 功能概述

两段"接入收尾/救火"流程:

- **公告场景(notice)**:选角成功(`SM_SELCHR(4017,param=1)`)后、进入 main 场景前的公告展示页。它**沿用当前 TCP 连接**(不新建),接收 `SM_SENDNOTICE(658)` 正文,玩家点确认后切往 main 场景,由 main 场景 ctor 回发 `CM_LOGINNOTICEOK(1018)` 作为"已读"回执。
- **断线重连**:notice/reconnect/main/select 四个场景共用同一套 `reconectFuc` 模板——弹"确定重连?"框,确定后用 `g_data.login.recIP/recPort/recSession` 重新拨号(**dataIndex=sessionid**),随后走 `SM_LOGIN → CM_RECONNECT(strs=reconnectID) → SM_LOGIN_AUTH(刷新 reconnectID) → SM_CHR_LIST(recog=1)` 的重连鉴权链。reconnect 场景是这条链的专职载体。

## 详细报文说明

### 1. 进入 notice 场景的条件(先澄清一个常见误解)

- **真正的进入点**:
  1. select 场景收到 `SM_SELCHR(4017,param=1)` 且非跨服返回(`g_data.areaChange` 为空)→ `game.gotoscene("notice")`(select.scene.lua:912-925);
  2. main 场景重连成功后的再入:`enterSelectScene` 中非排队路径会重发 `CM_SELCHR(角色名)` 并 `gotoscene("notice")`(main.scene.lua:277-286)。
- **与 `def.sfNotice` 无关**:`def.sfNotice` 由 `def.setSFNotice` 写入(def.init.lua:49-51),唯一消费点是 **sfselect 场景的私服公告**(sfselect.scene.lua:301-303,归 M2-S1)。notice 场景不读它。
- **连接归属**:notice 场景 ctor 仅 `net.add(self)`(notice.scene.lua:27),沿用 select 阶段的第②条连接(dataIndex=sessionid);只有其自身断线时的重拨才新建连接(见 §4)。

### 2. SM_SENDNOTICE(658) —— 公告正文

- **body**:整段文本,`net.str(buf)` 读全部字节并 GBK→UTF-8(notice.scene.lua:158-159)。
- **文本格式**(showNotice,行 30-61):
  1. 裁掉开头的空格(0x20)与 ESC(0x1B)字节;
  2. 删除所有反斜杠 `\`;
  3. 按 ESC(`string.char(27)`)分段,**第 2 段(i==2)被丢弃**,其余 trim 后逐段一行显示。
- **客户端后续动作**:渲染公告 + 确定按钮;确定(submitting 防抖)→ `net.remove(self)` → `gotoscene("main")`——**对 SM_SENDNOTICE 本身无回包**。

### 3. CM_LOGINNOTICEOK(1018) —— 公告确认/进图起点

- main 场景 ctor 第一件事就是 `net.send({CM_LOGINNOTICEOK}, nil, getRecord("TOsVersion3"))`(main.scene.lua:21-23)。
- **body 布局**:`TOsVersion3` 记录(packed,**80 字节**,globa2:269 起):major/minor/build/memSize/usingIGW/oemID 六个 int32(24B)+ cpuName char*47(48B)+ videoMemorySize int32 + isVirtualMachine int32(8B)。客户端**从未填充任何字段**(直接 getRecord 默认全零)——服务端勿信任其内容,只把它当"公告已确认,开始进图"的信号(M3-S1 从这里接手)。
- 若服务端把进图初始数据压在 CM_LOGINNOTICEOK 之后发送,时序天然满足(main 场景同时 `net.setWaitMsg(SM_NEWMAP, SM_MAPINFO_EX)` 只放行地图消息,main.scene.lua:24)。

### 4. reconectFuc 模板 —— 四场景共用的重连入口

notice/reconnect/main/select 四处的实现几乎逐字相同(以 reconnect.scene.lua:60-88 为例):

```text
弹窗 "<info>\n确定重连?" [取消|确定]
├─ idx==0(取消): common.gotoLogin{logout=true}   # net.close() + 回 login 场景
└─ idx==1(确定): self.reconnect = true
                  g_data.login.reconnectState = true
                  scheduler.performWithDelayGlobal(function()
                      net.connect(g_data.login.recIP, g_data.login.recPort, self,
                                  g_data.login.recSession)   -- 第4参=sessionid!
                  end, 0)
```

- **info 文案来源(触发点汇总)**:

| 场景 | 触发点 | 文案 |
|---|---|---|
| 全部四场景 | socketEvent status=2(连接失败) | "连接服务器失败…"/"连接服务器失败，请检查网络并稍后再试" |
| 全部四场景 | socketEvent status=3(断开) | "与服务器断开连接"(重连中则"连接超时中断，重连失败") |
| 全部四场景 | `onLoseConnect` | "网络连接已断开!" |
| 全部四场景 | `onNetworkStateChange`(WiFi/蜂窝切换检测,ping www.baidu.com) | "切换到 WIFI网络/蜂窝网络"或"网络连接已断开" |
| main/select | `SM_OUTOFCONNECTION_KICKOUT(4040)` | "已经被其他用户踢下线" |
| notice/reconnect | 同上 | 同上 |
| select | `SM_OUTOFCONNECTION(4018)` | "与服务器断开连接"(select.scene.lua:977-978;main 场景对该消息空处理) |
| **login** | socketEvent/onLoseConnect | 弹"重连"单按钮框,**但回调为空函数——按钮无效**,"重连"点了没反应(login.scene.lua:131-147);login 阶段真正出路是取消后手动重试或重启 |

- **dataIndex 语义差异(本篇核心)**:重连拨号把 sessionid 作为第 4 参传入,故新连接握手帧 dataIndex=**sessionID**(`net.connect` 第 5 参 areaid 缺省);而首连是 areaID。服务端必须同时接受两种语义并按值找回状态:areaID 定位大区配置,sessionID 找回 `SM_SELECT_SERVER.recog` 签发的会话(见主模块专节)。

### 5. CM_RECONNECT(4031) —— 重连鉴权上行

- **触发**:重连新连接握手完成后,服务端下发 `SM_LOGIN(4003)`(notice/reconnect/main/select 四处 processMsg 的 SM_LOGIN 分支完全一致,如 reconnect.scene.lua:168-174)→ 客户端回:

| 字段 | 值 | 说明 |
|---|---|---|
| recog/param/tag/series | 未设置(record 默认 0) | |
| strs | `{g_data.reconnctID}` | body = 0x00 前导 + GBK reconnectID |

- reconnectID 的来源:最近一次 `SM_LOGIN_AUTH(4004,param=1)` 中 TLoginIdResult2.reconnectID(string36,首字节长度 L+L 字节,M1-S3 §6)。若服务端从未下发 v2(v1 或无 body),reconnctID 为 nil → 此处 strs=nil → **无 body 的裸 CM_RECONNECT**((服务端需容忍))。

### 6. 重连链的服务端侧完整序列与应答布局

```text
net.connect(recIP, recPort, self, recSession)   ← 新 TCP,dataIndex=sessionID
│ ── cmd=24 握手
│◄─── SM_LOGIN(4003)
│──── CM_RECONNECT(4031) {reconnectID}
│◄─── SM_LOGIN_AUTH(4004, param=1) [TLoginIdResult2 87B]   ← 滚动下发新 reconnectID
│     (param=2 中间态可忽略;错误分支同 M1-S3 §6)
│◄─── SM_CHR_LIST(4010, recog=1)                            ← 重连成功的实际信号
│◄─── SM_LOGIN_ALREADY_ONLINE(4041, recog=0)(可选顶号询问)
```

- **SM_RECONNECT 应答布局?——不存在**:任务假设"data.login 或 reconnect.scene 解析 SM_RECONNECT"在代码中无对应物:
  - `SM_RECONNECT` 常量被 globa1 二次赋值覆盖(584 行 =4031 → 991 行 =802),运行时指 802;
  - main/select 场景对它的分支是空操作(`-- Nothing`,main.scene.lua:356-357、select.scene.lua:1011-1012),notice/reconnect 场景根本没有该分支;
  - `mir2.data.login.lua` 无任何 SM_RECONNECT 解析代码。
  - 结论:**重连成功与否,客户端完全以 `SM_CHR_LIST(recog=1)`(+可选 `SM_LOGIN_ALREADY_ONLINE(recog=0)`)判定**。服务端不要发 4031 下行期待识别(发了会被当未知消息丢弃;ident=802 则被空分支吞掉)。
- **各场景消费 SM_CHR_LIST(recog=1)**:
  - **reconnect 场景** `enterSelectScene`(reconnect.scene.lua:120-147):`receiveChrs` 渲染角色 → 若处于主动重连态(reconnect 标志)则清标志、跑进度条,5 秒后无弹窗即 `gotoscene("select")`;否则立即切换。进度条自身超时兜底:`showProgress` 走满 1.1 也自动切 select(行 15-51)——即使服务端不再发任何包,玩家也会离开重连页(但角色数据缺失,(未核实后续表现))。
  - **main 场景** `enterSelectScene`(main.scene.lua:258-295):清地面/UI 与 g_data → 5 秒后:若 `isLoginQueue`(排队中断线)→ 回 select 场景;否则**重发 `CM_SELCHR(角色名)` + 再次进入 notice 场景**(公告重看一遍)。服务端要准备好在同一会话上再次接收 CM_SELCHR。
  - select 场景:`reconnectState` 为真时只缓存 roleInfo(select.scene.lua:884-892),由后续 ALREADY_ONLINE 流程接管。

### 7. SM_LOGIN_ALREADY_ONLINE / CM_LOGIN_ALREADY_ONLINE 在重连链上

- notice 场景(notice.scene.lua:194-217):recog=1 → 弹"此账号目前在线,是否强行登录?";确定 → `gotoscene("reconnect")`(交给专职场景走完链路);取消 → `common.gotoLogin{logout=true}`;两条路径都回 `CM_LOGIN_ALREADY_ONLINE param=1/0`。recog≠1 → 直接 `gotoscene("reconnect")`。
- select 场景(select.scene.lua:1013-1035):同构,但确定后同样转 reconnect 场景。
- reconnect 场景(reconnect.scene.lua:206-228):recog=1 询问,确定(idx=1)→ 用缓存的 roleInfo 调 `enterSelectScene`;recog≠1 → 直接 `enterSelectScene`。
- main 场景(main.scene.lua:358-377):recog=1 询问,确定 → 自身 `enterSelectScene(roleInfo)`;recog≠1 → 同。
- 服务端语义不变:recog=1 必须等待 CM 回包再决定踢谁;recog=0 是免询问放行。

### 8. 失败与退出分支

| 分支 | 行为 |
|---|---|
| SM_OUTOFCONNECTION_KICKOUT(4040) | notice/reconnect/select/main → reconectFuc("已经被其他用户踢下线");login 无分支 |
| SM_OUTOFCONNECTION(4018) | select → reconectFuc("与服务器断开连接");main 空处理;其余不处理 |
| SM_SELCHR_ERR(4042) | notice:延时 1 秒弹"服务器维护中，请稍后再试",确定 `gotoLogin`;reconnect/main:同文案,确定 `gotoLogin`/bigExit |
| ident=11706(硬编码,仅 main 场景,main.scene.lua:388-393) | 弹"重连失败,请重新登陆",确定 `bigExit()`(清数据回登录)。这是服务端**主动宣告重连失败**的唯一通道;11706 无常量名,globa1 中不存在该数值的命名常量 |
| 重连拨号再次失败 | socketEvent(status=2/3)再次弹 reconectFuc,reconnect 态文案变"连接超时中断，重连失败" |
| 取消/回登录 | 一律 `common.gotoLogin`:net.close() → login 场景(logout 参数控制是否显示区服列表层,M1-S1) |

## 服务端实现要点

1. **recIP/recPort/recSession 的生命周期**:三者来自首次 `SM_SELECT_SERVER(4002)` 后一直驻留内存,进程不死就有效;跨进程重启后的有效性由服务端自行决定(sessionID 失效策略未核实)。重连握手的 dataIndex=sessionID 是服务端找回会话的唯一钩子,失效时应让握手后的 `SM_LOGIN→CM_RECONNECT` 链走到 11706(重连失败)而不是静默挂起。
2. **滚动 reconnectID**:每次重连鉴权通过都应在 `SM_LOGIN_AUTH(param=1,TLoginIdResult2)` 里下发新的 reconnectID(客户端无条件覆盖 `g_data.reconnctID`);旧值在被成功使用前保持可用,配合单点登录互踢。
3. **卡死点(不回包后果)**:
   - 重连握手后不发 SM_LOGIN → 客户端永远显示"正在重连中..";
   - 收到 CM_RECONNECT 后既不发 CHR_LIST 也不发 11706 → 玩家卡在重连进度条走完后的问题状态(数据不全);
   - notice 场景不发 SM_SENDNOTICE → 公告页空白但确定按钮仍可用(确认流程不依赖正文);
   - 不接受 CM_LOGINNOTICEOK 不影响客户端(它只是上报),但 M3 进图数据应以收到它为起点。
4. **互踢协议**:顶号统一用 `SM_OUTOFCONNECTION_KICKOUT(4040)`(文案固定"已经被其他用户踢下线",四个场景生效);`SM_OUTOFCONNECTION(4018)` 只有 select 场理会,别用它做顶号。
5. **公告文本编码**:GBK;分段符 ESC(0x1B);**第 2 段会被客户端丢弃**(历史行为,服务端拼文本时第 2 段不要放有效内容);反斜杠会被整体删除。
6. **CM_LOGINNOTICEOK body 是 80 字节全零 TOsVersion3**,校验长度即可,内容无意义。
7. **login 场景的"重连"按钮无效**(回调为空函数):HTTP/首连阶段的断线只能靠玩家重启或重试,服务端无需为此做任何配合,但排障时别期待该按钮产生流量。
