# M6-S2 商店买卖

> 所属主模块:[M6-NPC与商店](../主模块/M6-NPC与商店.md)

## 功能概述

NPC 商人交易共五类通道,全部挂在 `mir2.scenes.main.panel.npc.lua` 的 NPC 面板上:

1. **买入**:服务端脚本响应 `@buy` 类命令下发 `SM_SENDGOODSLIST(645)`(分类列表)→ 玩家点带子级的分类发 `CM_USERGETDETAILITEM(1015)` 拉明细(`SM_SENDDETAILGOODS(652)`,可翻页)→ 点购买发 `CM_USERBUYITEM(1014)`,应答 `SM_BUYITEM_SUCCESS(650)` / `SM_BUYITEM_FAIL(651)`。
2. **出售**:服务端发 `SM_SENDUSERSELL(646)` 打开"出售"拖拽框 → 物品入框即查价 `CM_MERCHANTQUERYSELLPRICE(1012)`,应答 `SM_SENDBUYPRICE(647)` → 确认发 `CM_USERSELLITEM(1013)`,应答 OK/FAIL。**5 秒节流**。
3. **修理**:与出售同构,`SM_SENDUSERREPAIR(668)` / `CM_MERCHANTQUERYREPAIRCOST(1024)` / `SM_SENDREPAIRCOST(671)` / `CM_USERREPAIRITEM(1023)` + OK/FAIL。
4. **寄存/取回**:寄存拖拽框 `SM_SENDUSERSTORAGEITEM(700)` → `CM_USERSTORAGEITEM(1031)` → `SM_STORAGE_OK/FULL/FAIL`;取回由独立仓库面板完成(M5-S3),共用 `CM_USERTAKEBACKSTORAGEITEM(1032)`。
5. **合成与兑换**:配药列表 `SM_SENDMAKEDRUGITEMS(712)` → `CM_USERMAKEDRUGITEM(1034)`;兑换框 `SM_OPEN_COMMIT_ITEM(4635)` → `CM_COMMIT_ITEM(4634)` → `SM_COMMIT_ITEM(4634,同号回执)`。

**关于 g_data.shop(`mir2.data.shop.lua`)**:`mir2.scenes.main.scene.lua :: scene:onEnter`(行 65)调用 `g_data.shop:init()`,其实现仅一行——`IAP.setEvtListener(self)` 注册充值事件回调,**既不清商品缓存也不属于 NPC 商店**。该文件真正与服务端相关的是元宝商城数据层:解析 `SM_SHOPITEMS(812)` 的 `TClientShop` 数组、IAP/GHOME 充值订单族(CM_GHOME_PAY_READY 4482 等),这些归 M8-S4,本文末尾仅作边界备查。

## 详细报文说明

### SM_SENDGOODSLIST(645)— 商品分类列表

- **处理位置**:`mir2.scenes.main.ui.lua :: mainui:processMsg`(行 700)→ `panel.npc.lua :: npc:showList(..., "goods")`。
- **TDefaultMessage 字段**:recog=商人 id(后续所有买卖请求的 recog);param=商品条目数 count;tag/series 未使用。
- **body 布局**:count 条 `PNewMarketInfo`(非 packed,对齐后单条 **32 字节**):

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | string[15] | kindName | 分类名(首字节长度 L+L 字节 GBK,占位 16B) |
| 16 | int | nextFlag | 子级标志:**>0 表示该分类还有明细**,点击后客户端发 CM_USERGETDETAILITEM |
| 20 | int | mPrice | 显示价格("xxx 金币") |
| 24 | int | mCount | **服务端商品标识 serverIdx**(买入时拆进 param/tag) |
| 28 | int | itemIndex | 物品索引,用于查 def.items 取外观 looks |

- 客户端本地按每页 10 条分页显示(纯 UI 翻页,不发包)。同时自动弹出背包面板。

### CM_USERGETDETAILITEM(1015)/ SM_SENDDETAILGOODS(652)— 明细与翻页

- **发送时机**(`panel.npc.lua :: clickBuy` 行 713-721 与 `clickPrev/clickNext` 行 662-702):
  - 分类条目 `nextFlag > 0`:发 `{CM_USERGETDETAILITEM, recog=merchant}`,body={kindName}(无 param);
  - 明细列表翻页:上一页 `param=max(0, menuIdx-10)`,下一页 `param=menuIdx+10`(下一页无上界校验,客户端可能越界请求,服务端需容忍返回空列表),body={上次请求的 kindName}。翻页**无节流**。
- **SM_SENDDETAILGOODS 字段**:recog=商人 id;param=条目数 count;**tag=本次数据的偏移 menuIdx**(客户端存为翻页基準并回传)。
- **body 布局**:count 条 `TClientItem`(packed=true,单条 = 16 + KeyValueSize×4 字节):

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | uint | makeIndex | 明细条目唯一标识,买入时拆进 param/tag |
| 4 | short | Index | 物品索引(def.items 外观等) |
| 6 | short | dura | **显示为"持久: dura/1000"**(Word 无符号化后整除 1000) |
| 8 | short | duraMax | **在此列表中被当作单价显示:"duraMax 金币"**(代码原文如此,服务端必须把售价放进 duraMax!) |
| 10 | short | KeyValueSize | 扩展键值对个数 n |
| 12 | uint | _Reserved | 保留 |
| 16 | dynamicArray | extendFields | n × TClientKeyValue(short ValueType + short ValueNumber = 4B) |

- 价格来源结论:分类列表用 `PNewMarketInfo.mPrice`;明细列表用 `TClientItem.duraMax`。不存在独立 tPrice 字段的传输(tPrice 仅是 TStdItem 结构内的静态字段,M5-S1)。

### CM_USERBUYITEM(1014)— 买入

- **触发时机**:`panel.npc.lua :: clickBuy`(行 704 起)。节流:`socket.gettime() - lastTime.buy > 0.5` 才放行,发送前立即置时间戳(`g_data.client:setLastTime("buy", true)`)。
- **TDefaultMessage 字段**:

| 字段 | 用法 |
|---|---|
| recog | 商人 id |
| param | Loword(serverIdx):分类购买= PNewMarketInfo.mCount;明细购买= TClientItem.makeIndex |
| tag | Hiword(serverIdx)(同上) |
| series | 未使用 |
| body | {物品名}(GBK 字符串段;分类购买=kindName,明细购买=TClientItem 名字) |

- **SM_BUYITEM_SUCCESS(650)**:recog=**玩家最新金币值**(经 `common.goldChanged` 更新并在增加时提示"+N 金币");param/tag=MakeLong 组成所购条目的 makeIndex,客户端把它从打开的商品列表中移除(`npc:removeItem`)。**所购物品本体不经此消息下发**,走普通入包消息族(SM_ADDITEM(200) 等,见 M5-S1)。收到后清 buy 节流戳。
- **SM_BUYITEM_FAIL(651)**:recog 错误码与文案映射(`ui.lua` 行 728-747):

| recog | 客户端弹窗文案 | 服务端含义 |
|---|---|---|
| 1 | 此物品被卖出. | 已售罄 |
| 2 | 您无法携带更多物品了. | 背包满 |
| 3 | 您没有足够的钱来购买此物品. | 金币不足 |
| 其它 | "未知错误: <recog>" | 自定义码(客户端不识别) |

### 出售链路:SM_SENDUSERSELL(646)→ 查价 → CM_USERSELLITEM(1013)

1. `SM_SENDUSERSELL`:recog=商人 id,其余字段未使用。客户端 `npc:showSellFrame(recog,"sell")` 打开右侧拖拽框并弹出背包。
2. 物品拖入(`addSellItem` 行 838):客户端先把该物品从背包**乐观移除**,随即发 `CM_MERCHANTQUERYSELLPRICE(1012)`:recog=商人,param=Loword(makeIndex)、tag=Hiword(makeIndex),body={物品名}。
   - 服务端回 `SM_SENDBUYPRICE(647)`:recog=价格。显示规则(行 766-769):recog≥0 显示 "<recog> 金币",负数显示 "???? 金币"。该分支同时服务修理报价(SM_SENDREPAIRCOST 同一 else-if)。
3. 玩家点"确定"(`clickSellOk` 行 897):**节流 5 秒**(`lastTime.sell`),通过后记录 `lastSellItem` 并发 `CM_USERSELLITEM(1013)`:recog=商人,param/tag=makeIndex 拆分,series=sp 或 0(出售框 sp 恒空 → 0),body={物品名}。
   - 若玩家把物品拖回/关框,`delSellItem` 把乐观移除的物品放回背包,不发任何包。
- **SM_USERSELLITEM_OK(648)**:从背包彻底删除该物(makeIndex 取自 lastSellItem),清节流与暂存。金币变化由独立的 `SM_GOLDCHANGED(653)` 下发。
- **SM_USERSELLITEM_FAIL(649)**:物品退回背包,弹窗列出可能原因:绑定物品和高级物品无法出售 / 请前往对应商店出售 / 可携带金币超出上限(未验证角色 200 万、已验证角色 5000 万)。同样清理状态。

### 修理链路:SM_SENDUSERREPAIR(668)/ CM_MERCHANTQUERYREPAIRCOST(1024)/ SM_SENDREPAIRCOST(671)/ CM_USERREPAIRITEM(1023)

- 流程与出售完全同构(拖拽框类型 "repair"):查价消息换成 `CM_MERCHANTQUERYREPAIRCOST(1024)`,应答 `SM_SENDREPAIRCOST(671)`(recog=费用,同一显示分支);确认消息为 `CM_USERREPAIRITEM(1023)`,字段布局同卖出(param/tag=makeIndex,series=sp 或 0,body={物品名}),5s 节流共用 lastTime.sell。
- **SM_USERREPAIRITEM_OK(669)**:param=修理后 dura,tag=修理后 duraMax,客户端写回 lastSellItem(此时物品已被 `delSellItem` 放回背包,故直接反映到背包数据)。清状态。
- **SM_USERREPAIRITEM_FAIL(670)**:物品退回背包,弹窗 "您不能修理此物品."。
- **特修说明**:本客户端**没有**独立的特修消息——不存在 `CM_REPAIR`、`SM_SENDCUSTOMOK` 等常量(grep 全树无定义);普通修理与特修若要区分只能靠不同 NPC/不同费用,(未核实)旧服务端是否以 series 区分,本客户端恒发 0。

### 寄存链路:SM_SENDUSERSTORAGEITEM(700)/ CM_USERSTORAGEITEM(1031)/ 应答三件套

- `SM_SENDUSERSTORAGEITEM`:recog=商人 id → 打开 "保管物品" 拖拽框。
- 确认寄存有两条路径:
  1. NPC 拖拽框(`clickSellOk`,type="storage")→ `CM_USERSTORAGEITEM(1031)`;
  2. 仓库面板(`panel.storage.lua :: putInItem` 行 303)→ 同一条 `CM_USERSTORAGEITEM(1031)`:recog=self.merchant(仓库主人 id,来自 SM_SAVEITEMLIST),param/tag=makeIndex 拆分,body={物品名}。仓库面板路径不填 series(npc 路径 series=sp 或 0)。
- 应答(共用分支,ui.lua 行 867-911):
  - `SM_STORAGE_OK(701)`:lastSellItem/storageItem 从背包删除并加入仓库面板;
  - `SM_STORAGE_FULL(702)`:弹窗 "你的个人仓库已满，你不能再寄存任何物品。";
  - `SM_STORAGE_FAIL(703)`:tip "寄存失败。"。
  三者都会清节流与暂存;失败时物品退回背包。
- 取回:实际由仓库面板 `getBackItem`(行 327)发 `CM_USERTAKEBACKSTORAGEITEM(1032)`(字段布局同上)。应答:
  - `SM_GETSTORAGEITEM_OK(705)`:recog=makeIndex(会顺手从 npc 商品列表 removeItem);
  - `SM_GETSTORAGEITEM_FAIL(706)`:recog=-1 超重 / -2 交易中禁用仓库 / -3 仓库被 CD 卡或密宝绑定;
  - `SM_GETSTORAGEITEM_FULLBAG(707)`:背包满。
  注:`panel.npc.lua :: showList/clickBuy` 中存在 type=="storage" 分支(读 TClientItem、发 CM_USERTAKEBACKSTORAGEITEM),但本构建中没有任何 SM 会以 "storage" 类型调用 showList(ui.lua 只传 goods/goods_detail/synthesis)——**该分支是死路径**,取回交互实际全在仓库面板(M5-S3)。

### 配药(合成)链路:SM_SENDMAKEDRUGITEMS(712)/ CM_USERMAKEDRUGITEM(1034)/ SM_MAKEDRUG_FAIL(714)

- `SM_SENDMAKEDRUGITEMS`:布局与 SM_SENDGOODSLIST 相同(recog=商人,param=count,tag=menuIdx,body=PNewMarketInfo 数组),但 showList 以 "synthesis" 类型渲染——条目名取 kindName、价格取 mPrice、serverIdx 取 mCount。
- 点击购买(`clickBuy`,type="synthesis")发 `CM_USERMAKEDRUGITEM(1034)`:recog=商人,param=Loword(mCount)、tag=Hiword(mCount),body={kindName};与买入共用 0.5s buy 节流。
- `SM_MAKEDRUG_FAIL(714)` 错误码(ui.lua 行 855-866):

| msg.recog | 文案 |
|---|---|
| 2 | 合成成功，获取物品失败 |
| 3 | 金币不够 |
| 4 | 材料不足 |

- `SM_MAKEDRUG_SUCCESS(713)` 在本构建无处理分支(定义未使用);(未核实)成功后的材料扣除/成品入包是否全部依赖通用物品消息族下发,重写时建议以通用入包消息为准并实测。

### 兑换链路:SM_OPEN_COMMIT_ITEM(4635)/ CM_COMMIT_ITEM(4634)/ SM_COMMIT_ITEM(4634)

- `SM_OPEN_COMMIT_ITEM`:recog=商人 id,**series=兑换序号 sp**(原样保存并在确认时回传),body=`net.str(buf)` 兑换提示文本(直接作为拖拽框标题)。
- 玩家放入物品点确认(`clickSellOk`,type="exchange")发 `CM_COMMIT_ITEM(4634)`:recog=商人,param/tag=makeIndex 拆分,**series=sp**,body={物品名};5s 节流(lastTime.sell)。
- 回执 `SM_COMMIT_ITEM` **与 CM 同号(4634)**,方向区分靠 ident 方向约定:

| msg.param | 客户端行为 |
|---|---|
| 1 | 成功:物品从背包删除(先 delSellItem 再删 lastSellItem),清节流与暂存 |
| 0 | 失败:delSellItem 物品退回背包;若 bufLen>0,把 body 文本作为绿色系统聊天消息显示 |

### "请酒"(playDrink)死路径

`clickSellOk` 支持 sell.type=="playDrink" → `ident=CM_USERPLAYDRINKITEM`,且 `setSellText` 有对应标题"请酒"。但:
1. `CM_USERPLAYDRINKITEM` 在 rebuilt-src 全树(含 mir2.def.globa1.lua)**没有定义**,运行时 ident=nil;
2. 没有任何调用方以 "playDrink" 类型调用 showSellFrame。

因此该功能在本客户端不可达,服务端无需实现。(未核实)旧版协议中请酒可能使用其它消息号。

## 边界备查:g_data.shop 与元宝商城(详见 M8-S4)

- `mir2.scenes.main.scene.lua :: onEnter` → `g_data.shop:init()` = `IAP.setEvtListener(self)`(注册充值回调,无缓存清理语义)。
- `SM_SHOPITEMS(812)`(ui.lua 行 1770):bufLen=0 直接忽略;否则 `g_data.shop:parseBody` 按 `bufLen / getRecordSize("TClientShop")` 循环解 `TClientShop` 记录,**looks==0 的条目丢弃**,余下按记录内 page 字段分组缓存到 `self.goods[page]`,交给 `panel.shop:processUpt(msg.param, items)` 渲染。
- `SM_FIRSTSHOP(815)` → `parseSpecially`:同记录解析,固定存入 `goods[5]`(特惠页)。
- `TClientShop`(非 packed,单条 **180 字节**):string name[15] / string typeName[15] / short looks / short page / short price / short curPrice / short type / short count / short effCount / uint effOffSet / string descStr[127];descStr 字段自偏移 52 起占 128B。
- 购买:`panel.shop.lua` 发 `CM_REQSEESHOP(1046)`(recog=页签类型)拉列表;确认框后发 `CM_DOSHOP(1048)`(recog=1,body={物品名})。
- 失败 `SM_DOSHOP_FAIL(816)`(ui.lua 行 1790 → `panel.shop.onDoShopFail`)错误码映射:0 非法物品名 / -1 不存在你想购买的物品 / -2 请先进行元宝充值 / -3 你帐号中的元宝数不够 / -4 你无法携带更多的物品 / -5 购买物品不在商城中 / -6 您的购买速度过快 / -8 您的专属元宝不足 / -9 您不是主宰者不能购买。注意源码中 `-8` 分支重复出现两次(反编译产物),第二个 `-8→荣耀点不足` 为不可达死分支,-9 实际映射"您不是主宰者不能购买";其余码落入 "你无法购买 err:N"。

## 服务端实现要点

1. **两段式商品结构**:先发 PNewMarketInfo 分类表(32B/条,count 在 msg.param),nextFlag>0 的分类等待客户端用**分类名**(GBK 字符串)拉明细;明细必须用 TClientItem 承载,且**售价放在 duraMax 字段**(客户端硬编码显示 "duraMax 金币"),真实持久放 dura(展示时 ÷1000)。这两处字段挪用是重写最容易踩的坑。
2. **商品标识双轨**:分类级购买用 `PNewMarketInfo.mCount` 作 serverIdx,明细级购买用 `TClientItem.makeIndex`;两者都以 Loword→param / Hiword→tag 拆分传输(int 高 16 位在 tag)。服务端必须能凭 (param,tag)+名字定位条目。
3. **节流契约**:买入 0.5s、卖出/修理/寄存/兑换 5s 由客户端本地强制,但服务端不应依赖它防刷(-6 "购买速度过快" 说明商城侧另有服务端节流);同时注意失败应答也会清客户端节流戳,可立即重试。
4. **乐观 UI 与最终一致性**:出售/寄存/修理在发确认包前客户端已把物品从背包摘下,服务端的成败应答决定它是被删除还是退回——**每个提交消息必须恰好回一个成败消息**,否则物品会停留在"悬空"状态(不显示于背包也无法恢复)。买入成功后金币用 SM_BUYITEM_SUCCESS.recog 同步,物品另走入包消息族,两条都要发。
5. **报价查询必答**:CM_MERCHANTQUERYSELLPRICE / CM_MERCHANTQUERYREPAIRCOST 的应答 SM_SENDBUYPRICE / SM_SENDREPAIRCOST 用 recog 传价格,负数会被显示为 "???? 金币"(可作为"无法评估"语义);不回包则拖拽框价格栏一直停留为空。
6. **SM_COMMIT_ITEM 与 CM_COMMIT_ITEM 同号(4634)**,服务端解析下行帧时按 SM 分支处理即可,不要因数值相同而漏发回执;param=0 时可在 body 附 GBK 失败文案(客户端显示为绿色聊天行)。
7. **死路径清单(无需实现)**:NPC 列表的 storage 取回分支、playDrink 请酒、SM_MAKEDRUG_SUCCESS、SM_HIDEMERCHANT_QUERY(见 M6-S1)。实现它们不会有任何客户端效果,但发了也不致错。
