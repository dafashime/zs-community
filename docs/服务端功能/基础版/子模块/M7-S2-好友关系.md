# M7-S2 好友关系

> 所属主模块:[M7-社交系统](../主模块/M7-社交系统.md)

## 功能概述

好友体系由三张关系表组成:**好友(friend)**、**关注(attention)**、**普通黑名单(blackList)**。服务端持有关系数据,通过"全量下推 + 增量更新 + 上下线通知"三种 SM 维护客户端缓存 `g_data.relation.*`;增删操作以名字为键经 CM 报文请求,应答用同号报文的 recog 携带错误码。另含**查看他人信息**(CM_QUERYUSERSTATE)与**附近玩家列表**(CM_QUERY_NEARBYPLAYER)两个支撑功能。

私聊聊天记录(`relation.chatRecord`)完全保存在本地 cache,**没有历史记录同步协议**;黑名单过滤、私聊未读计数均为纯客户端行为。

## 详细报文说明

### 全量列表:CM_QUERY_*(4430/4431/4432) ⇄ SM_SEND_*(同号)

上行无字段无 body。

下行:`param` = 记录条数 n;body = n 条连续记录,无额外分隔:

**TClientFriendRelation**(非 packed,对齐后 **36 字节**,globa2.lua L2460):

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | string[15] | name | 名字,char 区 N+1=16B,GBK,余量补 0 |
| 16 | short | level | 等级 |
| 18 | byte | job | 职业(0 战士/1 法师/2 道士) |
| 19 | string[15] | guildName | 行会名,16B |
| 35 | byte | isonline | 1 在线 / 0 离线 |

**TClientAttentionRelation**(非 packed,**22 字节**,L2484):name16 + level(short) + job(byte) + color(byte,关注显示颜色索引) + isonline(byte) = 21 → 22。

**TClientNormalBlackRelation**(非 packed,**20 字节**,L2507):name16 + level(short) + isonline(byte) = 19 → 20。

客户端校验:按 param 循环 `net.record` 解码,不检查 bufLen 总量(relation.lua :: decodeArray_ L26)。排序规则(本地):在线优先,再按等级降序。

### 添加/删除:CM_ADD_* / CM_DEL_*

统一格式:strs={目标名}(单条 GBK 字符串),无 record body。发送点:panel.relation.lua L1379–1425、panel.group.lua L567–614、panel.guild.lua L4598–4644。

各应答的错误码 recog 分支(panel.relation.lua L1296–1377 文案表,数值即服务端返回值):

| 操作 | 成功 | 错误分支 |
|---|---|---|
| 加好友 SM_ADD_RELATION_FRIEND_OK/FAIL | OK:4433,buf=对方名 → 提示"XX 同意成为您的好友" | FAIL:4434,recog=-1 不在线或名字错,-2 不能添加自己,-3 已是好友,-4 好友人数达上限,-5 其他失败 |
| 加关注 4435 | recog=0 | -1 名字为空,-2 不在线或名字错,-3 不能关注自己,-4 关注人数上限,-5 对方已被关注 |
| 加黑名单 4436 | recog=0 | -1 名字为空,-2 不在线或名字错,-3 不能添加自己,-4 黑名单上限,-5 已在黑名单 |
| 删好友 4437 | recog=0 | -1 不能删除自己,-2 对方不是好友 |
| 取消关注 4438 | recog=0 | -1 对方未被关注 |
| 移出黑名单 4439 | recog=0 | -1 对方未被加入黑名单 |

注意:加好友是唯一有独立 OK/FAIL 双号的操作(4433 成功时带对方名,说明**对方需要确认**——"同意成为您的好友";其余操作即时生效)。是否真有对方确认环节由服务端决定,客户端只认这两个号的到达时机((未核实)服务端是否在对方同意后才回 4433)。

### 增量更新:SM_UPDATE_RELATION_*(4441/4442/4443)

来源:`ui.lua` L2010–2015 → `relation:updateFriend/updateAttention/updateBlackList`(relation.lua L101–172)。

### 上下线通知:SM_RELATION_MEMBER_ONLINE(4444)/ OFFLINE(4445)

`relation:setOnline_`(relation.lua L182):body = 单条 GBK 名字;`param` 选择目标表:**0=好友,1=关注,2=黑名单**;在线/离线由 ident 区分,客户端置该成员 isonline 并重排列表。

### 查看他人信息:CM_QUERYUSERSTATE(82) → SM_SENDUSERSTATE(751)

上行:strs={目标名}。发送点:panel.relation.lua :: showInfo L1466、panel.group.lua L556、panel.guild.lua L4588、console.widget.lock.lua L60。

应答 body = **TUserStateInfo**(packed=true,globa2.lua L2914,不填充):

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | int | feature | 外观 feature 整型值 |
| 4 | string[15] | userName | 名字,16B |
| 20 | byte | nameColorIndex | 名字颜色索引 |
| 21 | byte | milrankSW | 军衔/标识位 |
| 22 | byte | b2 | 保留 |
| 23 | byte | vipFlag | VIP 标记 |
| 24 | string[15] | guildName | 行会名,16B |
| 40 | string[15] | clanName | 战队名,16B |
| 56 | array[16]×record TClientItem | userItems | 对方身上装备,固定 16 槽 |

TClientItem(packed)= 16B 定长头(uint makeIndex + short Index + short dura + short duraMax + short KeyValueSize + uint _Reserved)+ KeyValueSize 条 TClientKeyValue(short ValueType + short ValueNumber,各 4B)。整包尺寸 = 56 + Σ(16+4×KeyValueSize_i)。

处理(ui.lua L403–439):guildName 与上次不同才刷新头顶行会名缓存;打开 equipOther 面板展示对方装备。

### 附近玩家:CM_QUERY_NEARBYPLAYER(4414) ⇄ 同号下行

上行(relation.lua :: getNearList L253 / panel.group.lua L182):

| 字段 | 值 |
|---|---|
| param | 客户端本地收集的可见玩家数 n |
| body | n 条 `{"string", 名字, 15}`(每条 = 长度字节 + ≤15B GBK 名字) |

注意 panel.group 只在 n>0 时发送;relation:getNearList 无条件发送(n 可为 0)。

下行:`param`=条数,body = n 条 **TClientNearbyPlayerInfo**(非 packed,**36 字节**,globa2.lua L2522):name16 + level(short) + job(byte) + sex(byte,0 男/1 女) + guildName16。分发 ui.lua L1182,同时喂给组队面板 near 页与好友面板 near 页。

### SM_NotifyGroupMessage(4412)

`ui.lua` L1194:`name = net.str(buf)`;recog=1 向通知中心添加一条 "FriendApply"{名字,param 业务码},否则移除同名通知。从常量名看似组队相关、从 notice 类型看是好友申请,**实际业务语义未核实**;服务端可将其用于"有人申请加您好友/入队"的红点提醒。

## 服务端实现要点

1. 三张关系表的增删改都要**同时维护双方视角**:对操作者回错误码/成功,对被操作方(若可见)下发对应的 SM_UPDATE_RELATION_* 增量。
2. 全量列表在登录后主动下发一次(客户端切页也会主动拉取,双保险);之后靠 4441–4445 维持一致性,避免反复全量。
3. 上限类错误码(-4)分别对应好友/关注/黑名单各自容量,由服务端配额决定。
4. CM_QUERYUSERSTATE 是高频查看接口,建议做频率限制(客户端已有 queryOther lastTime 节流辅助);userItems 固定填 16 槽,空槽用全 0 的最小 TClientItem(KeyValueSize=0)。
5. CM_QUERY_NEARBYPLAYER 的上行名单来自客户端本地 AOI,**不可信任**:服务端应以自己视野计算为准重新校验后再返回。
6. 所有名字字段线上为 GBK;`string[N]` 类型占 N+1 字节且首字节为长度(变长 string 语义,BRIEF §6),非定长 char*。
