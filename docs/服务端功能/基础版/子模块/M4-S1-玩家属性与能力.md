# M4-S1 玩家属性与能力

> 所属主模块:[M4-战斗属性与技能](../主模块/M4-战斗属性与技能.md)

## 功能概述

服务端向客户端推送角色(及英雄)的全量能力数值、货币资本、体力/活力/经验池等标量状态;客户端解析后驱动血条、属性面板、金币显示等。本子模块只描述下行推送,不涉及任何上行请求——属性变更全部由服务端主动触发(登录进入游戏后、穿脱装备、升级、喝药、货币变动等时机,具体由服务端策略决定,客户端无对应 CM 请求)。

- **解析行为(服务端必须遵守的约束)**:`setAbility` 先 `net.record("TAllAbility", buf, bufLen)` 整包解出,再把字段**按名字**分发到本地三条记录 `ability(TAbility)`、`ability2(TSub2Ability)`、`ability3(TSub3Ability)`。因此:
  - 服务端必须按 TAllAbility 的完整布局发送,不能只发增量;
  - 字段顺序/偏移不可变,缺字节会导致后续字段整体错位。
- **应答与错误分支**:无应答概念。客户端收到后刷新血条、infoBar、属性页;若 `g_data.serverConfig.allowMaxLevel <= ability.level`(allowMaxLevel 为本地配置,默认 999,见 `mir2.data.serverConfig.lua`)则本地提示"您的等级已经达到上限…将不能再获取经验"(纯客户端文案,一句带过)。
- `SM_ABILITY_NOCAPABLE`:在 `mir2.def.globa1.lua` 中不存在该常量(已核实),本树客户端不支持此消息。

### SM_WINEXP(44)——获得经验

- 分发:行 365 → `g_data.player.ability:set("Exp", msg.recog)`。
- **字段**:

## 服务端实现要点

1. **属性必须全量推送**:SM_ABILITY 是唯一属性通道,无增量协议;每次变化(穿脱装、buff、升级)都应重发完整 TAllAbility(184B),并把金币放 recog、职业放 Byte(param)。
2. **bufLen 校验严格**:SM_GETDIAMNUM_EXT 必须恰好 24 字节;SM_ABILITY 虽无显式长度校验,但 net.record 按 TAllAbility 尺寸截断读取,短包会导致尾部字段缺失。
3. **param/recog 方向约定易错点**:SM_STAMINA/SM_VITALITY 的"上限"在 recog、"当前值"在 param;SM_WINEXP 的"新经验"在 recog 而"增量"拆在 param/tag。
4. **等级上限**:达到 allowMaxLevel(客户端本地默认 999)后客户端仍会显示经验获取,但提示无法再获经验;是否继续给经验由服务端决定(未核实)。
5. 推荐时机:登录进场景后先发 SM_ABILITY + SM_SENDMYMAGIC(M4-S2)+ SM_GETDIAMNUM_EXT,再补发各标量包,可保证面板首屏数据完整(客户端不做请求-应答配对,顺序仅影响显示时序)。
