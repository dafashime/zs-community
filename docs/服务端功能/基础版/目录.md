## 一、协议总览

### 1.1 传输与帧格式(小端)

一条 TCP 业务帧 = `TClientMessage` 头(12 字节)+ `dataLength` 字节载荷:

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | uint32 | sign | 固定魔数 `0xFF44FF44`(4282711876) |
| 4 | uint8 | reservationByte | 平台码,固定 `2` |
| 5 | uint8 | cmd | 23=业务消息(`LM_DYN_ENCRYPT_CODE`) / 24=握手(`LM_GET_ENCRYPT`) / 25=心跳(`LM_PING`) |
| 6 | int16 | dataLength | 载荷字节数 |
| 8 | uint32 | dataIndex | 握手帧:= areaID 或 sessionID;业务帧:= 自增序号(初始 `random(65535)+1000`,每发一条 +1) |

cmd=23 时载荷 = `TDefaultMessage`(12 字节)+ body(`dataLength-12` 字节):

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | int32 | recog |
| 4 | int16 | ident(CM_*/SM_* 消息号) |
| 6 | int16 | param |
| 8 | int16 | tag |
| 10 | int16 | series |

服务端下行帧中,以下 ident 在网络层被特殊处理,不进普通分发队列:

- `SM_RUNGATEDYN`:网关动态加密回执。客户端把该 default+buf 原样再包一层 cmd=23 帧+TDefaultMessage 回发(`net.handler`,`mir2.single.net.lua`)。
- `SM_ACT_GOOD` / `SM_ACT_FAIL`:直接分发。
- 其余 ident 进入消息队列,由 `net.processLoop` 每帧处理(≤30ms 切片);`net.setWaitMsg(ident,...)` 可令队列只放行等待的消息,其余暂存——这决定了**某些请求在收到特定应答前,后续应答不会到达各场景**,服务端重写时必须保证关键链路必回包。

### 1.2 连接生命周期

1. HTTP 阶段:登录中心 `/account` 等接口取得游戏网关 ip/port 与会话信息 → 见 [M1-S1](子模块/M1-S1-HTTP登录中心接口.md)。
2. TCP 连接:`net.connect(ip, port, target, sessionid?, areaid?)`,dataIndex 取 areaID(首连)或 sessionID(公告/重连场景)——语义差异见 [M1](主模块/M1-登录与接入.md)。
3. 连接成功后立即发握手帧(cmd=24,platformCode=2,dataIndex 同上),此后所有业务帧用 cmd=23 封装;详见 [M1-S2](子模块/M1-S2-TCP握手加密与心跳.md)。
4. 心跳:cmd=25(LM_PING),无 TDefaultMessage 无 body;当前构建仅 DEBUG 下定时发送并测量往返延迟(`net.sendPing` / `net.processLoop`)。
5. 断线重连走独立场景流程,见 [M1-S4](子模块/M1-S4-公告与断线重连.md)。

### 1.3 发送侧组装(net.send)

`mir2.single.net.lua :: net.send(msg, strs, data)`:

- `msg[1]`=CM_* 消息号;`msg.recog/param/tag/series` 可选,填入 TDefaultMessage;
- `strs`:字符串数组,逐条 UTF-8→GBK(u2a)后写入;多条之间留 1 个 `0x00` 分隔字节;body 总长额外 +1 字节(收尾占位);
- `data`:record(getRecord 构造的结构体)或类型化数组 `{ {"byte",v} / {"short",v} / {"int",v} / {"uint",v} / {"ID",v} / {"char*",s,len} / {"string",s,len} }`;
- 位段助手:`Lobyte/Hibyte`(param 双字节拆分)、`Loword/Hiword`(双 MakeIndex 打包进 param/tag)等定义于 globa1/globa2。

### 1.4 记录(record)系统与服务端编码义务

记录定义于 `mir2.def.globa2.lua`,类型语义(Mir2ByteStreamCompat.cpp 为准,**一律小端**):

| 类型 | 线上尺寸 | 编码 |
|---|---|---|
| byte | 1 | 无符号单字节 |
| short | 2 | 小端 int16 |
| int / uint | 4 | 小端 int32 / uint32 |
| double / ID | 8 | 小端 IEEE754 double(ID 类唯一 id 以 double 承载) |
| char* (声明长 N) | N+1 | 定长 GBK 字节区:内容不足补 0x00,读取按 N+1 截取 |
| string (声明长 N) | N+1 | 变长:**首字节 = 长度 L**,后跟 L 字节 GBK |
| record | 嵌套尺寸 | 递归展开 |
| array N of X | N × 元素尺寸 | 定长数组 |
| dynamicArray | 动态 | 按 len 字段循环读取 |

**对齐规则(重写服务端最容易踩坑)**:非 packed 记录按 C 风格自然对齐——short 成员对齐到 2,int/uint/double 对齐到 4/8,整条记录总尺寸向上取整至最大成员对齐值(`generateConfigs/fillCheck`)。`packed=true`(如 TLoginIdResult)不填充。因此记录线上尺寸 ≠ 字段简单相加。

线上文本一律 **GBK**(客户端在边界做 u2a/a2u 转换)。118 个记录的完整字段表随域展开在各子模块文档中,提取底稿另存于仓库外 `工作底稿（未随仓库分发）/records.txt`。

### 1.5 分发架构(谁接收报文)

只有 5 类对象注册为 net target 并实现 `processMsg(defaultMsg, buf, bufLen)`:

- 场景:login / notice / reconnect / select / main(`net.add(self)`);
- main 场景的 `ui`(中央分发器,2607 行 switch)、`ground`(对象感知)、以及 map/role 的二级分发。

面板(panel)/数据模块(data.*)从不直接收包,均由 ui.lua/ground.lua 分支调用其方法。因此追踪某 SM 的处理位置,入口固定在这几个文件。

## 三、使用须知

- **消息号数值**:每份文档中的 `CM_XXX(nnnn)` 数值都直接来自 `mir2.def.globa1.lua`;跨主模块共享的报文(如系统消息八件套、TClientItem 结构)只在归属子模块详述一次,其余处以链接引用。
- **常量重定义陷阱**:`mir2.def.globa1.lua` 存在同名字段二次赋值,**运行时以后一次赋值为准**(Lua 语义)。已核实案例:`SM_RECONNECT` 先 4031(行 584)后 802(行 991),客户端实际按 **802** 收发;服务端重写必须以各子模块速查表中核实的运行时值为准,勿直接抄首次定义。
- **回包义务**:凡客户端用 `net.setWaitMsg` 等待的应答(如 SM_NEWMAP、SM_LOGON),若服务端不回应答,后续消息将被扣留在队列中,表现为"卡住"——各子模块"服务端实现要点"一节均有标注。
- **编码**:所有字符串字段 GBK;JSON 接口(HTTP)为 UTF-8 文本但账号密码字段可能经 GBK 处理,以 M1-S1 实测代码为准。
