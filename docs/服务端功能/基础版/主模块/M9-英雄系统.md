## 模块边界

本文档系列覆盖基础版客户端(`client/src/`,下称"本树")中**英雄(Hero)实体**相关的全部客户端↔服务端交互:

- **M9-S1**:英雄的召唤(CM_HERO_LOGON)/收回(CM_HERO_LOGOUT)、目标锁定与守卫(CM_HERO_APPTARG)、状态开关(CM_HERO_CHGSTATE、`@RestHero` 聊天命令)、以及服务端下发的英雄身份/属性/成长/合击/醉酒等状态报文(SM_HERO_LOGON/NAME/ABILITY/LEVELUP/UNIONSTATUS 族)与英雄专属战斗动作报文(SM_HERO_RUSH/LONGHIT/LASTHIT,处理逻辑引用 [M4-S3](../子模块/M4-S3-物理攻击与受击.md))。
- **M9-S2**:英雄背包与英雄装备栏两条独立容器(数据层 `g_data.heroBag` / `g_data.heroEquip`)的全部操作报文:主角背包↔英雄背包互转(CM_HERO_TOHEROBAG/TOHUMBAG 及其应答)、英雄背包内堆叠(CM_PILEUPITEM series=1)、英雄穿戴/脱下/使用/丢弃(CM_HERO_TAKEON/TAKEOFF/EAT/DROPITEM)及对应 SM 应答族、英雄技能列表下发与技能开关(CM_HERO_SKILL_HOTKEY)。

**不在本模块范围**(如实记录边界,不脑补):

- 主角自身的背包装备流程见 [M5](M5-物品与装备.md);英雄报文与其一一成对,本模块只写英雄侧并给出对照。
- 英雄施法/攻击的通用协议(CM_SPELL、物理攻击族)见 [M4](M4-战斗属性与技能.md)。**本树客户端从不代替英雄发送 CM_SPELL**——全部 `net.send({CM_SPELL,...})` 调用点(settingLogic.lua 410/425/474、btnCallbacks.lua 1032、controller.lua 591)均基于 `g_data.player` 数据,是主角自身的施法;英雄战斗由服务端 AI 驱动,客户端仅通过 CM_HERO_APPTARG 指定目标/守卫点(`mir2.scenes.main.console.autoRat.lua` 中无任何英雄相关逻辑,grep 核实)。
- 常量表中存在大量英雄扩展消息号(时装、天赋、宝石、体质、多英雄选择等,详见下方"已定义但未使用"清单),**本树无任何发送/接收代码**,服务端若实现这些功能不能以本树为协议依据。

## "series/isHero 区分约定"专节(服务端重写关键)

英雄与主角在协议中并存,本树共出现四种区分模式。重写服务端时必须逐条消息核对它属于哪一种:

### 模式 A:独立消息号段(主流,绝大多数英雄报文)

英雄操作**不复用主角消息加标志位**,而是使用独立消息号,数值集中在两个连续段:

- CM 段:`CM_HERO_LOGON`(1050)~`CM_HERO_SKILL_HOTKEY`(1109),外加 `SM_TOHEROBAG`/`TOHUMBAG` 应答段 817~820;
- SM 段:`SM_HERO_QUITMAGIC`(896)~`SM_HERO_HELPOP_OK`(925),外加 `SM_GLORYFEALTY`(960,虽无 HERO 前缀但 ui.lua 只写入 `g_data.hero`)。

主角侧对应消息见对照表(M9-S2)。**注意例外**:英雄属性不是"SM_ABILITY 加 series 区分"——客户端解析代码证实两者是不同 ident 的同构报文:`SM_ABILITY`(52)由 `mir2.data.player.lua :: setAbility` 解析,`SM_HERO_ABILITY`(900)由 `mir2.data.hero.lua :: setAbility` 解析,二者 body 同为 `TAllAbility`,param 低字节同为职业;差异仅在 SM_ABILITY 的 recog 承载金币而 SM_HERO_ABILITY 忽略 recog。

### 模式 B:同一 CM 消息用 series 区分容器归属(仅 CM_PILEUPITEM 一例)

`CM_PILEUPITEM`(1115)三个发送点,series 三种取值:

| 发送点 | series | 含义 |
|---|---|---|
| `mir2.scenes.main.ui.lua :: processMsg → PileUpItem(isHero)`(行 230-247) | `isHero and 1 or 0` | 自动整理:1=英雄背包,0=主角背包 |
| `mir2.scenes.main.panel.bag.lua :: putItem`(行 247-253) | 0 | 主角背包手动拖拽堆叠 |
| `mir2.scenes.main.panel.heroBag.lua :: putItem`(行 258-264) | 1 | 英雄背包手动拖拽堆叠 |

字段布局一致:`recog`=目标格物品 makeIndex,`param`=Loword(源物品 makeIndex),`tag`=Hiword(源物品 makeIndex)(32 位 makeIndex 拆成 param/tag 两个字)。仓库(storage.lua 行 387-393)也复用此消息且 series=0。服务端必须按 series 决定在哪个容器执行堆叠。

### 模式 C:同一 SM 消息按 msg.recog==roleid 区分对象(英雄状态同步)

若干状态类 SM 对主角和英雄共用一个消息号,客户端以 `msg.recog` 与已知 roleid 比较:

| 消息 | 判定代码位置 | 英雄侧行为 |
|---|---|---|
| SM_STRUCK(31) | `mir2.scenes.main.ground.lua :: processMsg`(行 508-538) | `self.player.hero and self.player.hero.roleid == msg.recog` → 写 `g_data.hero.ability` 的 HP/maxHP/MP/maxMP |
| SM_HEALTHSPELLCHANGED(53) | ground.lua(行 572-618) | 同上判定;更新后刷新 heroHead |
| SM_DRINK_STATUS(2816)/SM_DRINK_DRUG_STATUS(2817)/SM_DRINKEXP_STATUS(2818) | ground.lua(行 692-741) | `msg.recog == g_data.hero.roleid` → `hero:setdrinkStatus/setdrinkDrugStatus/setWineExp(msg.param, msg.tag)` |

前提:客户端必须先收到 SM_HERO_LOGON(899)记录 `g_data.hero.roleid`,否则这些共享报文无法归户。**recog 是唯一的归户依据,不存在额外标志位。**

### 模式 D:UI 层 isHero/formPanel 决定发哪个消息号(客户端内部分支,不影响线上格式)

同一交互动作,按物品来源面板选择英雄版或主角版消息号,线上报文结构完全相同:

- `mir2.scenes.main.common.item.lua :: use`(行 399-414)/`getItemSourceInfo`(行 304-319):`formPanel.__cname == "bag"` → `CM_TAKEONITEM`(1003)/`CM_EAT`(1006);否则 → `CM_HERO_TAKEON`(1102)/`CM_HERO_EAT`(1104)。
- `mir2.scenes.main.common.item.lua :: takeOff`(行 546-572):主角 → `CM_TAKEOFFITEM`(1004);英雄 → `CM_HERO_TAKEOFF`(1103)。
- `mir2.scenes.main.common.item.lua :: throw`(行 574-662):主角 → `CM_DROPITEM`(1000);英雄 → `CM_HERO_DROPITEM`(1106)。
- `mir2.scenes.main.common.settingLogic.lua :: update/useItem`(行 138-197)、`missHp`(行 497-600):`isHero and CM_HERO_EAT or CM_EAT`;保护策略里 `heroExit` 发 CM_HERO_LOGOUT。
- 数据层镜像:`mir2.data.heroBag.lua` = `clone(bag)` + `isHero=true`,`mir2.data.heroEquip.lua` = `clone(equip)` + `isHero=true`;`bag:useEnd("take")` 内据 `self.isHero` 把物品写入 `g_data.heroEquip` 或 `g_data.equip`(mir2.data.bag.lua 行 553-560)。
